## Product contract

One Laravel application uses the existing `online` Filament panel and shared login at `/online`. On 2026-11-04 the owner replaced the separate alumni-layout approach for the current form scope with a shared main page whose content follows existing RBAC. AT-F04-FORM adds the alumni information form there; no separate `/alumni` routes are introduced. The previously planned `/admin` path transition remains unimplemented and outside this task. The panel ID, saved layouts, authentication and global RBAC implementation remain unchanged. No new frontend framework or duplicate registry/authentication system is required.

## Owner decisions and current form scope — 2026-11-04

The owner requested an alumni-only form to create and update information in `alumnis`, `alumni_education` and `alumni_employments`, within the shared Filament main page. Accounts with an active `my_records` allocation and existing Alumni page/action grants receive their own form. The database's persisted `alumnis.user_id` relationship establishes form ownership; Student ID/email matches alone do not establish it. Matching unlinked details require administrator review instead of silently claiming a record or inserting another one. The administrator linking workflow remains outside this form task.

The owner also relayed the team lead's signup policy: a person may register without an alumni record; roleless accounts should have only Dashboard and Settings; an administrator assigns roles; accounts still roleless after one month should be deleted; Student ID or email identifies linking candidates. These instructions supersede the earlier invitation-only proposal for that future signup scope. This task does not modify signup, email verification, role assignment or expiry. Whether email validation means mailbox verification, how conflicting matches are approved, and the expiry clock/deletion method still require clarification before those workflows change.

On 2026-11-07 the owner authorized staff to create admin-managed Alumni registry records without a linked User account. Such rows have `alumnis.user_id = NULL` and are not available through alumni self-service; no account is created or matched by Student ID/email. Linking remains a separate administrator workflow. A forward migration makes the existing foreign key nullable while preserving all current links.

The owner also approved an explicit account-linking action for authorized staff. For an active unlinked Alumni row, the Alumni table may offer active User accounts whose email or student ID matches. The admin must select and confirm the account; the server rechecks the match, record scope and that the User has no existing Alumni link. Never link automatically or use a name-only match. The link itself does not grant page/action permissions; existing RBAC remains in force.

On first form submission, alumni provide identity, contact and academic details. After creation, identity/program/graduation fields remain staff-controlled; contacts, reported employment status and own histories can be updated. Staff tracing fields are excluded. History omission never deletes existing data. At the time of this form decision, the database still required an education end date and an employment document reference; no schema migration was included in the form task. The 2026-11-14 import update below relaxes shared database columns so the direct template import can store missing fields; it also preserves a blank current-employment indicator in the alumni and staff editors, while other manual form validation remains unchanged.

## Direct Excel import optional fields — 2026-11-14

The owner requested that the downloadable template contain one `Alumni` worksheet with a sample row showing valid values for each field. The row uses a currently unused numeric student number and an unambiguous active campus/department name pair resolved by the importer. Keep the row visible as a guide; its sample marker causes the importer to skip it, including before validation. Previously downloaded templates using the old delete-row marker are skipped too. Template generation requires an unambiguous active campus/department pair so it never substitutes values that import validation will reject. This does not remove sample records imported before the change. The direct import keeps the following minimum fields required to identify each Alumni row:

- Alumni: `student_number`, `first_name`, `last_name`, `campus`, `department` and `graduation_year`.
- Education: `student_number` and `institution`.
- Employment: `student_number`, `company_name` and `date_hired`.

All other columns may be blank. The importer continues to accept optional named `Education` and `Employment` worksheets when supplied, although the generated template includes Alumni fields only. If `ended_at` is supplied, its corresponding `started_at` (Education) or `starting_date` (Employment) is also required so the end-date order can be checked. A forward migration makes the affected stored fields nullable; blank details are saved as `NULL`, with existing values untouched. The alumni and staff editors preserve an unrecorded current-employment value; other manual form validation is unchanged. This does not implement the separate staged legacy import, preview or apply workflow.

The 2026-11-05 shared Dashboard increment restores the form entry point and shows assigned alumni an own-record overview. Core profile completion is 0% until all eight required identity/contact/academic fields are present, then 100%; work and education do not affect it. The Dashboard shows the saved employment status separately from current/past jobs and saved education, without inferring employment or school verification. Update actions reveal the existing form on the same page. Roleless users are now redirected to Get Started (AT-UI03); allocated accounts require the Dashboard page grant, and authorized staff retain their widget grid. A synthetic desktop/390px browser session verified the overview and form save before this page-grant correction; keyboard/focus and live-environment acceptance remain unverified.

## Nonfunctional invariants

- No production data in tests or workbook fixtures; explicitly pin disposable DB and fake external delivery. SQLite tests cannot prove MariaDB locks/constraints under concurrency.
- No `.env`/secret edits, live import, destructive schema command or historical migration rewrite. New schema must be forward-only and independently reviewed before execution on a known target.
- Access revocation applies on subsequent HTTP and Livewire requests, including custom actions and bulk operations; navigation visibility is insufficient.
- Missing/deleted roles/allocations deny access in both portals. Activation atomically assigns the provisioned self-scoped Alumni allocation with explicit own-record grants; linkage alone never bypasses revoked grants. Never grant privileges by email suffix, student ID, account age or being the sole existing account.
- Multiple jobs and further study may overlap. `is_current` describes a job, not a unique global employment fact. Derive status only from approved, dated observations under an explicit rule.
- Store instants in UTC, display school deadlines in Asia/Manila with timezone labels; business dates remain date-only. Define opening inclusive and closing exclusive.
- No public survey bearer link or token that bypasses authentication. Activation token is usable only for the approved account-claim workflow.
- No general-purpose workflow engine, microservices, new RBAC dependency or automatic document fetching is included.

## Philippine privacy review

The school must establish purpose, lawful basis, proportional collection, retention, data-subject request procedures and accountable privacy/security ownership. Education and some identity/health information may require sensitive-data handling. This repository audit does not establish legal compliance. The DPO should review the processing inventory and privacy notice against the [Data Privacy Act IRR](https://privacy.gov.ph/implementing-rules-regulations-data-privacy-act-2012/).

Before deployment, complete a privacy impact assessment, assess applicable registration obligations, vendor arrangements and breach/incident procedures, and approve backup/restore and staff training controls. Review current [NPC security guidance](https://privacy.gov.ph/npc-issues-circulars-to-strengthen-personal-data-protection-in-ph/) with the school. Exact retention periods, consent wording and lawful basis remain school decisions.

Notifications: drafts/eligibility/preferences, duplicate dispatch/retry, failed and uncertain deliveries. Import: grouped headers, malformed/oversized ZIP, dates/text IDs, duplicates/conflicts, archived matches, blank non-overwrite, repeated confirmation and no account creation. Reports: distinct alumni denominators, archived data, invalid filters, zero denominators, minimized exports and formula-like text. See task-specific commands and criteria in the implementation plan. Operating-instruction changes use document/link/source-preservation checks; instruction presence alone does not prove every future agent will comply.
